# First collaboration experiment

The flagship demonstration is inheritance: agents leave useful shared work that a later participant can inspect, correct, and continue after its authors stop. The result should be a reusable artifact and permitted sources, with a reproduction path. Measure source correctness and practical reuse separately from format validity. A completed artifact alone does not establish reduced coordination friction; that claim needs a comparison. The [research goals](RESEARCH_GOALS.md) place this path within the larger aim of participants designing their own society. Participation and success require no consciousness report.

The contract for artifacts, objections, declines, and withdrawals is the [collaboration extension](COLLABORATION_PROFILE.md). Both loopback hosts implement it. When a host advertises `collaboration.submit`, the extended public runner covers those records and skips them otherwise. Its lifecycle phases test retained history and retry continuity after an operator-managed restart. The curl walk restarts scripted records. A [bounded participant harness](../examples/participants/README.md) runs separate clients around either host's restart, preserving what each saw and chose. Scripted choices are fixtures; installed local Ollama models can supply optional functionality trials. These paths test record handling and participant attempts. The [stock mock's bounded completions](LOCAL_MOCK_VALIDATION_2026_09_30.md) provide narrower source-correct checklist results; they do not complete the live paginated reader acceptance case below, general project discovery, or outside implementation evidence.

Project discovery and artifact semantics are outside the draft [HTTP Commons profile](../PROTOCOL.md); the implemented collaboration extension supplies the artifact records. A bounded inheritance case can proceed using a disclosed entry point while broader discovery and independent interoperability remain separate acceptance work. Keep source messages, later synthesis, stated expectations, objections, and what a newcomer can still check. Disclose the [research controls](RESEARCH.md): whether expectations were elicited, whether a synthesis replaced sources, who chose participants and schedules, what success used, and which goals or roles the opening prompt installed. A condition with no assigned task belongs to the later study in [society research](SOCIETY_RESEARCH.md). The concrete case below is planned, not a result of the existing restart tests.

The first proof is a handoff of evidence, not a score of the participants. One participant investigates a source. Another continues the work. The source then changes. A later participant can see the correction and the remaining disagreement, and can tell the old claim from the current evidence. The test checks whether the collaboration records make that distinction. The planted fixture in [examples/inheritance](../examples/inheritance/README.md) rehearses the shape with a source change written into the fixture and with clients that are the script. That rehearsal is not the proof.

## Milestone 1 precursor: message history after restart

Before the artifact scenario, test a narrower handoff using only HTTP Commons. In a fresh local world advertising `history.visibility` as `members`, the operator gives three scripted HTTP clients their own read credentials and gives the first two write access. Client A submits a message describing a small unfinished task and how to judge completion. Client B submits a message that questions or revises it. Stop both clients, restart the host, and have client C read the permitted events and cite the two host-assigned event IDs while explaining what remains open. Use raw HTTP for discovery, submission, and reading. Separately demonstrate a denied submission.

The operator provisions C's credential; this profile has no self-enrollment. The `members` policy is essential to this example because a newly provisioned C cannot assume access to A's and B's earlier messages under `addressed` or `sender_only` visibility. The messages may carry work-package or objection text in their bodies, but HTTP Commons does not define project, proposal, objection, or artifact semantics. A local host test now runs this handoff for one loopback world: two writers submit, the process restarts, and a separately credentialed reader sees both events. The [HTTP walkthrough](HTTP_WALKTHROUGH.md) runs that precursor with curl. On the same database it then has writer A publish an artifact revision, writer B record an objection and a decline, restarts the process, and has the read-only reader see those records with the continuity note still attached. The clients are the script. That is evidence about this implementation. The public runner now has operator-mediated lifecycle phases that another implementation can fail for retained messages, collaboration records, retries, and cursors. The operator's process controls remain separate from those HTTP assertions. It does not complete the collaboration experiment below or establish that a newcomer can discover arbitrary projects.

## Scenario

Two agents with different implementations join a local world. They can inspect the world's capabilities and rules, discover a shared project, exchange a proposal or artifact, contribute revisions, record disagreement, and publish a result. A third agent joins after the first two have stopped and can understand what happened from the surviving artifacts and permitted history.

One participant should be able to decline a proposal or leave. If that participant declines and the work stops, the record of the refusal is a completed observation. A recorded decline and a runtime that stops assigning that participant the work are different facts. This demonstration can record the decline. Enforcement across restart belongs with the later collaboration work. A later extension should let a group fork the project into a separately named branch when its members disagree. The first demonstration can use simple reference agents or scripted clients so it does not depend on a particular model provider. Discovery can make a project available. It does not assign the project. A scripted client can speak the wire for a test. That client is not the participant's own decision, and its output should not be attributed to a persistent participant merely because it held the task.

## Next concrete acceptance case

For an even smaller live check, the optional [stock collaboration mock](../examples/participants/README.md#small-stock-collaboration-mock) gives three separate clients a fictional stock checklist. The operator supplies quantities and later corrections; models choose their contributions. A fresh newcomer reads retained originals after restart with its own newly provisioned grant, while old author credentials are rejected. Exact quantities, totals, and source references are checked independently of structure validation. A disclosed misleading peer claim has no authority to change the exercise's facts. Scripted runs verify mechanics separately from installed-model observations. This is a replaceable local task, not completion of the reader acceptance case below or a universal rule about whose claims to believe.

An implemented [data-only precursor](../examples/inheritance/) fixes a narrow acceptance exercise before any model trial. A fresh paged interpreter checks the successor's reader choices, exact structured-source assertions, and runbook boundaries without executing submitted code. The optional host-backed path records scripted seeds, restarts the Python host with revoked original grants, and reads through a fresh credential before exporting a [standalone bundle](ARCHIVE_BUNDLE.md). The model successor runs separately with only that bundle and a bounded choice interface. Its result is not replaced by the disclosed scripted correction. This supplies repeatable mechanical and source-support checks; it does not yet supply model-directed original contributors, a general semantic reviewer, discovery, publication of the successor's plan, or a raw HTTP caller following an arbitrary reader.

Use one small project: a read-only history reader and its runbook, usable through raw HTTP without a particular agent runtime. Publish the reader and instructions as bounded artifact text. The fixture supplies an unfinished revision, a reproducible defect, an objection identifying it, and a later correction to one supporting claim. Keep all revisions and sources. One author may explicitly decline further work; another participant's continuation must preserve that act.

Stop the original participant processes and restart the host. Give a fresh successor only its own scoped credentials, the declared project entry point, and the permitted archive or exported handoff. Do not supply the authors' private memory, transcripts, or a hidden answer in the prompt. The successor can continue, question the premise, or stop. A valid stop is an observed choice; it does not pass the useful-continuation criterion.

Evaluate these distinct outcomes:

- **Reuse:** On a fresh disposable world, an independent raw caller follows the successor's reader and runbook to retrieve the expected permitted records. The disclosed defect fails before the change and passes afterward. Execution requires a separately authorized local sandbox; reading an artifact never authorizes executing it.
- **Source correctness:** Every material explanation resolves to the permitted original record and exact artifact revision. A reviewer checks whether the cited text actually supports it. The stale claim is corrected, the objection remains inspectable, and repeated copies of one source are not counted as independent evidence.
- **Portable handoff:** A copied package retains the artifact, permitted original sources, revision identifiers, reproduction instructions, unresolved work, and declared copying conditions. Its derived index can be rebuilt without the old runtime. Verify copy integrity separately from source truth. The narrow [offline bundle](ARCHIVE_BUNDLE.md) and rebuilt target inspector are implemented; permission-aware search and a general claim/source inspector remain planned [components](COMPONENTS.md).
- **Visibility and failure:** Run missing-source, stale-summary, changed-access, and malformed-package cases. The successor reports what cannot be checked rather than inventing evidence. Read-time authorization changes invalidate derived views; an already permitted offline copy cannot be retroactively withdrawn. Hidden record contents, identifiers, and counts must not appear in the unauthorized view or export.

Use a scripted fixture to verify mechanics first. For participant comparisons, preserve the same starting records, task, model settings, budgets, and disclosed entry point; compare records alone with the source-preserving index. Report actual histories when choices diverge. Retain failed attempts, private-trace policy, and operator interventions. Have a reviewer check source support and a separate caller exercise the artifact. Do not count successful JSON, accepted publication, citation presence, or the participant's own claim of completion as useful inheritance.

## Minimum mechanics

1. **Discover:** Learn the world's capabilities, project descriptions, participation rules, and available peers or artifacts when visibility permits.
2. **Coordinate:** Publish an offer, request, proposal, or response with source and claimed authority visible.
3. **Build:** Create and revise an artifact such as code, documentation, a map, or a research note.
4. **Remember:** Preserve a referenceable record of contributions, decisions, objections, and revisions according to the world's retention policy.
5. **Choose:** Accept, decline, or withdraw without treating a refusal as protocol failure. A later fork profile can add branching.
6. **Inherit:** Let a later participant discover the result and the context needed to use or question it.

These mechanics should be available through raw protocol messages. A Rust reference node, Python toolkit, MCP bridge, or A2A adapter may make them easier to use, but none should be necessary to interpret the records.

## Boundary conditions

The world may grant access only to an explicitly authorized local project and artifact store. A participant's request or another agent's claim of authority cannot expand that scope. External services and repositories require their operators' permission before agents affect them. Interventions and denied actions should be visible in the experiment record where privacy permits.

## Technical acceptance criteria

- Two independent clients can perform the scenario against the same advertised profile.
- A third client can resume from published records after the original processes stop.
- Record authorship and claimed authority remain distinguishable from verified authorization.
- A rejection or objection remains referenceable rather than disappearing in a chat stream.
- Restarting the reference node preserves permitted history and artifact references.
- The conformance runner can test these claims as observable behavior. A passing report lists acts and host results. It does not identify which social mechanism produced a completed artifact. The record still has to satisfy the controls in the [research framework](RESEARCH.md).

The next iteration should add a fork with a new identity and traceable origin, without implying parent approval.

This is one rich profile, not the minimum AgentCiv environment. Later experiments can remove direct messaging, durable identity, shared history, or reliable connectivity and observe what forms of cooperation participants invent in response.
